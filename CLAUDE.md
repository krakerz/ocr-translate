# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`ocr-translate`: a Linux-first Rust tool that captures a screen region, OCRs it (Tesseract), sends the text to a configurable translation/LLM backend (with an optional fallback chain), and shows the result in a popup, recording it to a local history. Runs as a system tray app with a Capture/Live Clipboard Translate/History/Quit menu. **Targets Wayland only** (GNOME/KDE/wlroots) via the standard xdg-desktop-portal APIs — X11 sessions and any in-app global hotkey were deliberately dropped (see below); also builds on Windows/macOS with reduced portal/tray support.

## Build & run

```sh
cargo build --release
cargo build              # debug, faster iteration
cargo fmt                # always run before considering an edit done
cargo test               # no test suite exists yet; this just typechecks
```

There is no lint config beyond rustfmt — no clippy CI, no test suite. When changing behavior, verify manually (see "Manual verification" below); `cargo build` succeeding is not sufficient evidence a fix works, especially for anything touching capture/tray/clipboard code.

System dependencies (see README.md for distro package names): Tesseract + Leptonica dev libs, X11 dev headers (`eframe`'s windowing backend keeps an X11 fallback compiled in; XWayland is also used for the cursor-position/monitor-geometry queries below), GTK3 + libappindicator/libayatana-appindicator dev libs (tray icon).

CLI surface (`src/main.rs`): `ocr-translate run` (default — tray daemon), `capture` (one-shot: capture → crop → OCR → translate (with fallback) → popup → record history), `watch-clipboard` (watches the clipboard for text changes, translating each new value into a live-updating popup — never recorded to history), `test-provider [--provider NAME] TEXT` (exercises exactly one translate backend, bypassing fallback — the fastest way to test provider/prompt changes), `show-history <INDEX>` (0 = most recent; shows one entry in the popup — used internally by the tray's History submenu), `clear-history`, `init-config --format yaml|conf [--force]` (regenerates the default config; normally auto-created on first run).

## Architecture

**No X11 session support, and no in-app hotkey — both deliberately dropped.** Earlier versions had an X11 capture backend and a hotkey listener (X11 grab + a Wayland `GlobalShortcuts` portal attempt). Both are gone: the `GlobalShortcuts` portal only grants shortcuts to Flatpak/Snap-sandboxed apps in practice (confirmed by testing: a plain binary gets `NotAllowed: An app id is required`, and wrapping it in a matching systemd `app-<id>-<random>.scope` doesn't help either), so it never reliably worked; and once this app is Wayland-only, an X11-session capture backend serves no purpose. The tray's Capture item and `ocr-translate capture` bound natively in the user's DE/compositor (see README) are *the* way to trigger a capture now, not a fallback. Don't re-add either without new evidence the portal restriction is actually fixable.

**Process model is the load-bearing design decision here.** `ocr-translate run` (`src/daemon.rs`) starts a tray icon (GTK main loop, its own thread — `src/tray.rs`), then blocks on a channel for `DaemonEvent::{Capture, ShowHistory, ClearHistory, WatchClipboard, Quit}`. Critically, **`Capture`, `ShowHistory`, and `WatchClipboard` do not run their pipelines in-process** — they spawn `ocr-translate capture` / `show-history <N>` / `watch-clipboard` as fresh child processes (`daemon::spawn_subcommand`). This is not incidental: GTK's main loop (tray) and eframe/winit (the crop-selector/popup/live-translate windows) both talk to the Wayland connection, and doing both in one process on different threads was found to silently hang with no error. If you're tempted to inline those spawns back into the daemon process, don't — re-read the doc comment on `daemon::run` first. (`ClearHistory` has no GUI involved, so it runs directly in the daemon process.) `spawn_subcommand` also spawns a throwaway thread per child to call `Child::wait()` — dropping a `Child` does *not* reap it, so without this every spawned subcommand over a long-running daemon session accumulates as a `<defunct>` zombie (confirmed happening on a real long-running session before this fix).

**Config hot-reload** (`daemon::watch_config`) is a natural consequence of the above plus a small addition: since each `capture`/`show-history` child process reloads config from disk itself, everything they use (providers, prompt, OCR, popup sizes, capture backend, history settings) is *already* live-reloaded for free — no extra plumbing needed. `watch_config` mainly exists to keep the tray's `Arc<RwLock<AppConfig>>` handle (shared with `tray::spawn`) up to date, so its periodic History-submenu refresh reads current settings (e.g. `tray_menu_entries`) without a restart. A config file that fails to parse mid-edit is logged and the previous valid `AppConfig` is kept rather than swapped in.

**The actual one-shot pipeline** lives in `main.rs::run_capture_cycle_inner` and is the same code path whether invoked via `ocr-translate capture`, spawned by the daemon, or bound to a key in the user's DE: `capture::acquire()` → `ocr::recognize()` → `translate::translate_with_fallback()` → `popup::show_result()` → `history::append()`. Any error surfaces via `popup::show_error()` too, since this typically runs headless (triggered by a keybind/tray, no attached terminal).

**Capture backend selection** (`src/capture/mod.rs::acquire`) branches on `cfg.capture.backend`:
- `BuiltIn` (default): `grab_active_monitor()` always goes through `capture/portal.rs` (xdg-desktop-portal `Screenshot`, the only portable way to get pixels on Wayland — there is no X11 fallback), then `select_crop()` shows it in our own zoom/pan/select window (`capture/selector.rs`; there's no portable "overlay the live desktop" API on Wayland, so this grabs a full still image first rather than a live overlay). Crops down to just the monitor under the cursor rather than handing OCR the whole multi-monitor desktop; `capture/pointer.rs` gets cursor position and `capture/monitor.rs` gets monitor layout, both via a direct XWayland query (works even though this is a Wayland session — XWayland mirrors the real cursor position and output layout, and there's no portable Wayland API for either).
- `External` (`capture/external.rs`): runs a configurable shell command (default: KDE's `spectacle -r -b -c`) that does its own **live** region selection on the real desktop and leaves a PNG on the clipboard, then reads that back via `arboard` — no crop step needed, its output is already the selected region. Diffs the clipboard image against a pre-command snapshot to avoid mistaking a stale clipboard image for a fresh one (same guard the bash prototype this was based on used a hash-polling loop for). **`arboard` needs the `wayland-data-control` Cargo feature** (see comment in `Cargo.toml`) — without it, arboard silently uses its X11 backend even when `WAYLAND_DISPLAY` is set, and can't see what a Wayland-native tool like `wl-copy`/`spectacle` placed on the clipboard (confirmed by testing: `get_image()` returned `ContentNotAvailable` every time until this feature was added). Don't remove that feature flag.

**`capture/monitor.rs` queries monitor geometry via a direct XRandR `GetMonitors` request over `x11rb`** (with the `randr` Cargo feature enabled), not via `xcap` — a dependency this project used and dropped. `xcap` 0.9+ has every geometry accessor (`Monitor::x()/y()/width()/height()`, and `Monitor::from_point()`, which calls those internally) unconditionally call an internal Wayland scale-factor lookup that hangs indefinitely on at least this project's KDE/KWin test setup (confirmed by tracing the hang to `get_scale_factor()` → `libwayshot_xcap::WayshotConnection::new()`, which spams `Ignoring a wl_output with version < 4` and never returns) — and since this app is now always running under Wayland, there was no version of xcap that would avoid the bug. `x11rb` was already a dependency (used by `pointer.rs`), so replicating the one XRandR request xcap used internally, directly, removed the whole dependency. Don't reintroduce xcap for this.

**Config** (`src/config.rs`): lives in `~/.config/ocr-translation/` (Linux; `dirs::config_dir()` gives the OS-correct equivalent elsewhere), auto-created with a starter `config.yaml` plus `config.example.{yaml,conf}` reference copies on first run if missing. Both `.yaml` (via `serde_yaml`, full nested structure with `#[serde(default)]` at every level) and `.conf` (hand-written INI parsing in `load_ini`, since INI has no native nested-struct mapping) must be kept in sync manually — if you add a config field, update the relevant struct *and* `load_ini`'s match arms *and* both example files in `config/`. `ProviderConfig.kind` (`openai_compatible` | `google_translate` | `bing_translate`) drives which `translate/*.rs` implementation gets built in `translate::build_for`; `ProviderConfig.mode` (`public` | `private`) further branches Google/Bing between their free unofficial endpoint and their official authenticated API (ignored for `openai_compatible`). `popup` and `history_popup` are deliberately two separate `PopupConfig` sections with identical shape — the former sizes the live capture-result popup, the latter the one shown when reopening a history entry (`main.rs::show_history`) — so don't merge them back into one, that was a deliberate ask.

**Translation providers** (`src/translate/`) all implement the small `Translator` trait. `openai_compat.rs` is the general-purpose one — it's how LM Studio, Ollama, OpenAI, and DeepSeek are all supported through a single implementation (any `/chat/completions`-shaped API), configured entirely via `ProviderConfig` (base_url/model/api_key) rather than needing provider-specific code. `google.rs`/`bing.rs` are real translation APIs (not LLMs, so they never send `prompt.system`/`prompt.template`), each with `mode: public`/`mode: private`:
- Google's `public` mode hits the free, unofficial `translate.googleapis.com/translate_a/single` endpoint (no key) — a real, widely-used technique, confirmed working, though it can be rate-limited by Google without notice.
- **Bing's `public` mode is a stub that always errors**, on purpose. The old free-token endpoint (`edge.microsoft.com/translate/auth`) is dead (404, confirmed by testing); the current bing.com/translator frontend instead calls an internal `www.bing.com/ttranslatev3` endpoint with tokens scraped from page HTML, and it's guarded by an abuse-prevention check (`ShowCaptcha`) that requires replaying the page-load session's cookies to pass (also confirmed by testing). That's session spoofing to dodge bot detection, not a stable public API — don't implement it. Bing only has a private (Azure API key) mode in practice.
- DeepSeek is `openai_compatible`, not a dedicated translation API — it has no free/public mode to add either; don't try to invent one.

`translate::translate_with_fallback` (`src/translate/mod.rs`) tries `active_provider` then each of `fallback_providers` in order, returning the first success — used by the real capture pipeline. `translate::build`/`build_named` (single provider, no fallback) are used by `test-provider`, which is deliberately not fallback-aware since its whole point is to surface one provider's real error.

**CJK font fallback** (`src/fonts.rs`): egui's bundled default fonts only cover Latin script, so Japanese/Chinese/Korean text rendered as tofu boxes until this was added. Rather than embedding a CJK font (a full-coverage one like Noto Sans CJK is ~20MB), `install_cjk_fallback` shells out to `fc-list :lang=ja file` (not `fc-match`, which happily returns an unrelated font even with zero CJK support on the system) to find whatever CJK-capable font is already installed, reads it from disk, and appends it as a fallback on egui's `Proportional`/`Monospace` font families. Confirmed this correctly loads a `.ttc` (TrueType Collection, e.g. `NotoSansCJK-Regular.ttc`) via `egui::FontData`'s face `index` field — not just plain `.ttf`/`.otf`. Every `eframe::run_native` closure in this crate (`popup.rs` ×2, `capture/selector.rs`, `live_translate.rs`) calls this on `cc.egui_ctx` before returning the app; do the same for any new window. If no CJK font is found, this is a silent no-op (logged at debug level) rather than an error — better to render boxes than to fail the whole popup.

**History** (`src/history.rs`): JSON Lines at `history.jsonl` next to the config file, one `HistoryEntry` per line, newest appended last, trimmed to `history.max_entries` on every append (the whole small file is rewritten each time — simplicity over micro-optimizing an infrequent, small-file operation). `load_recent(n)` returns the last `n` entries reversed (most-recent-first) for both the tray submenu and `show-history <INDEX>` (0 = most recent).

**Tray History submenu** (`src/tray.rs`): rebuilt periodically (every 2s) rather than once at startup, since captures run in a separate process (see above) — this process only learns about new entries by re-reading `history.jsonl` from disk. On Linux this refresh runs via `glib::source::timeout_add_seconds_local` on the GTK main-loop thread (not a plain `std::thread` + sleep) — GTK/muda tray objects must only be touched from the thread running the GTK main loop, so the refresh closure has to be scheduled onto that loop rather than mutating the `TrayIcon` from elsewhere. A cheap fingerprint (entry count + latest timestamp) avoids rebuilding the menu when nothing changed.

**Live Clipboard Translate** (`src/live_translate.rs`, `watch-clipboard`): a long-lived (not one-shot) eframe window with a background thread polling `arboard::Clipboard::get_text()` (same crate/feature as the image-clipboard `external` capture backend, so the `wayland-data-control` note above applies here too) at `live_translate.poll_interval_ms`. On each poll it compares the current text against the last value it translated (plain string equality; empty/whitespace-only text is skipped) and only re-translates on an actual change — this is intentionally simpler than `capture::external`'s snapshot-diffing, since there's no "stale clipboard from before we started" concern here: on startup it should immediately translate whatever's *currently* on the clipboard. Shared state (`Arc<Mutex<LiveState>>`) is written by the watcher thread and read each frame by the egui `update()`, which reuses `translate::translate_with_fallback` — same fallback chain as capture — but deliberately never calls `history::append`. Don't add a history write here; that's the one thing this command is explicitly not supposed to do.

## Manual verification

There's no automated test suite, so behavior changes need to be checked by hand:
- `cargo build && ./target/debug/ocr-translate capture` exercises the full pipeline directly (fastest loop for capture/OCR/crop-selector changes).
- `ocr-translate test-provider --provider NAME "some text"` exercises just the translate leg without any screen interaction — use this for prompt/provider changes.
- For the `external` capture backend, a real interactive test needs a human at the keyboard; to test the clipboard-diffing mechanics deterministically instead, set `external_command` to something non-interactive (e.g. `wl-copy < some.png`) and seed a *different* baseline image on the clipboard first — otherwise capturing the same bytes twice reads as "cancelled" (see the doc comment on `capture::external::capture`).
- Tray behavior needs an actual running desktop; a `com.canonical.dbusmenu` `Event` D-Bus call against the tray's menu object path (visible via `busctl --user` / the `org.kde.StatusNotifierWatcher`'s `RegisteredStatusNotifierItems`) can simulate a real menu click without needing to drive a mouse, which is how tray wiring (including the History submenu and Clear History) has been verified in this environment. Use `GetLayout` first to find the numeric ids of the items you want to click.
- Kill stray `ocr-translate` processes between test runs (`pkill -f ocr-translate`) — a killed-without-cleanup tray process can leave a stale, non-functional icon visible in the system tray that's easy to mistake for a live one.
