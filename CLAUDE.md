# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`ocr-translate`: a Rust tool targeting **Linux (Wayland) and Windows** — macOS isn't supported yet — that captures a screen region, OCRs it (Tesseract), sends the text to a configurable translation/LLM backend (with an optional fallback chain), and shows the result in a popup, recording it to a local history. Runs as a system tray app with a Capture/Live Clipboard Translate/Live Region Translate/History/Quit menu.

**Linux** is the mature, day-to-day-verified platform: **Wayland only** (GNOME/KDE/wlroots) via the standard xdg-desktop-portal APIs — X11 sessions and any in-app global hotkey were deliberately dropped (see below).

**Windows support is newer than Linux's but now confirmed working end-to-end** (see "Cross-platform capture" below and `TODO.md` for the full status): one-shot `capture` (`xcap`-backed) has been verified on a real Windows 11 VM (KVM/QEMU/libvirt) to produce a correct screenshot, correctly OCR real (Japanese) text via Tesseract, and correctly translate it via Google — not just compile. The tray (including right-click menu interaction) and Live Clipboard Translate are confirmed working there too. This took several real build-environment gotchas (see the Windows-specific notes further down and README's Requirements) plus several real runtime issues (missing runtime DLLs, a tray with no Win32 message pump, the VM's display having no OpenGL support, missing `tessdata`) — all found and fixed along the way, documented below. **Not yet tried on genuine physical Windows hardware** (only a VM so far) — that's still a meaningful gap worth keeping in mind (e.g. the OpenGL workaround below is VM-specific and shouldn't be needed on a real GPU driver), but "does the pipeline actually work" is no longer an open question. `watch-region` (Live Region Translate) isn't implemented on Windows at all yet, just a clear "not supported on this OS" error.

## Build & run

```sh
cargo build --release
cargo build              # debug, faster iteration
cargo fmt                # always run before considering an edit done
cargo test               # no test suite exists yet; this just typechecks
```

There is no lint config beyond rustfmt — no clippy CI, no test suite. When changing behavior, verify manually (see "Manual verification" below); `cargo build` succeeding is not sufficient evidence a fix works, especially for anything touching capture/tray/clipboard code.

System dependencies on Linux (see README.md for distro package names): Tesseract + Leptonica dev libs, X11 dev headers (`eframe`'s windowing backend keeps an X11 fallback compiled in; XWayland is also used for the cursor-position/monitor-geometry queries below), GTK3 + libappindicator/libayatana-appindicator dev libs (tray icon), PipeWire dev libs (`libpipewire-0.3`, used only by `watch-region`'s ScreenCast capture). On Windows: Tesseract + Leptonica via `vcpkg install tesseract:x64-windows` (`leptess`'s own documented approach, not pkg-config) — see `.github/workflows/autobuild.yml` for the exact CI setup.

CLI surface (`src/main.rs`): `ocr-translate run` (default — tray daemon), `capture` (one-shot: capture → crop → OCR → translate (with fallback) → popup → record history), `watch-clipboard` (watches the clipboard for text changes, translating each new value into a live-updating popup — never recorded to history), `watch-region` (picks a fixed screen region via a PipeWire ScreenCast session, then OCRs+re-translates it whenever the recognized text changes, in a live-updating popup — never recorded to history), `test-provider [--provider NAME] TEXT` (exercises exactly one translate backend, bypassing fallback — the fastest way to test provider/prompt changes), `show-history <INDEX>` (0 = most recent; shows one entry in the popup — used internally by the tray's History submenu), `clear-history`, `init-config --format yaml|conf [--force]` (regenerates the default config; normally auto-created on first run).

## Architecture

**No X11 session support, and no in-app hotkey — both deliberately dropped.** Earlier versions had an X11 capture backend and a hotkey listener (X11 grab + a Wayland `GlobalShortcuts` portal attempt). Both are gone: the `GlobalShortcuts` portal only grants shortcuts to Flatpak/Snap-sandboxed apps in practice (confirmed by testing: a plain binary gets `NotAllowed: An app id is required`, and wrapping it in a matching systemd `app-<id>-<random>.scope` doesn't help either), so it never reliably worked; and once this app is Wayland-only, an X11-session capture backend serves no purpose. The tray's Capture item and `ocr-translate capture` bound natively in the user's DE/compositor (see README) are *the* way to trigger a capture now, not a fallback. Don't re-add either without new evidence the portal restriction is actually fixable.

**Process model is the load-bearing design decision here.** `ocr-translate run` (`src/daemon.rs`) starts a tray icon (GTK main loop, its own thread — `src/tray.rs`), then blocks on a channel for `DaemonEvent::{Capture, ShowHistory, ClearHistory, WatchClipboard, WatchRegion, Quit}`. Critically, **`Capture`, `ShowHistory`, `WatchClipboard`, and `WatchRegion` do not run their pipelines in-process** — they spawn `ocr-translate capture` / `show-history <N>` / `watch-clipboard` / `watch-region` as fresh child processes (`daemon::spawn_subcommand`). This is not incidental: GTK's main loop (tray) and eframe/winit (the crop-selector/popup/live-translate/live-region windows) both talk to the Wayland connection, and doing both in one process on different threads was found to silently hang with no error. If you're tempted to inline those spawns back into the daemon process, don't — re-read the doc comment on `daemon::run` first. (`ClearHistory` has no GUI involved, so it runs directly in the daemon process.) `spawn_subcommand` also spawns a throwaway thread per child to call `Child::wait()` — dropping a `Child` does *not* reap it, so without this every spawned subcommand over a long-running daemon session accumulates as a `<defunct>` zombie (confirmed happening on a real long-running session before this fix).

**Single-instance lock, and why it's scoped only to `run`** (`daemon::acquire_single_instance_lock`): `ocr-translate run` takes an advisory OS file lock (`flock` via the `fd-lock` crate) on `daemon.lock` in the config directory, held for the process's whole lifetime. A second `run` that can't acquire it logs an error, shows an error popup ("ocr-translate is already running..."), and exits `Ok(())` — it does **not** attempt to kill, signal, or otherwise touch the instance already holding the lock. Verified: starting a second `run` while one is active leaves the first completely untouched (still alive, tray icon intact) and the second cleanly exits after its popup is dismissed. A file lock rather than a PID file: the OS releases it automatically on any exit (including a crash or `kill -9`), so there's no "is that PID stale or is it really still us?" logic to get wrong — a PID-file approach risks exactly the kind of process-identity mistake that could kill an unrelated process. **This lock intentionally does not extend to `capture`/`show-history`/`watch-clipboard`/`watch-region`** — those are the commands a hotkey binding actually invokes, and running several concurrently (a capture while `watch-region` is open, two captures in flight, etc.) is legitimate, expected behavior; don't couple their contention handling (if any is ever added) to this lock.

**Config hot-reload** (`daemon::watch_config`) is a natural consequence of the above plus a small addition: since each `capture`/`show-history` child process reloads config from disk itself, everything they use (providers, prompt, OCR, popup sizes, capture backend, history settings) is *already* live-reloaded for free — no extra plumbing needed. `watch_config` mainly exists to keep the tray's `Arc<RwLock<AppConfig>>` handle (shared with `tray::spawn`) up to date, so its periodic History-submenu refresh reads current settings (e.g. `tray_menu_entries`) without a restart. A config file that fails to parse mid-edit is logged and the previous valid `AppConfig` is kept rather than swapped in.

**The actual one-shot pipeline** lives in `main.rs::run_capture_cycle_inner` and is the same code path whether invoked via `ocr-translate capture`, spawned by the daemon, or bound to a key in the user's DE: `capture::acquire()` → `ocr::recognize()` → `translate::translate_with_fallback()` → `popup::show_result()` → `history::append()`. Any error surfaces via `popup::show_error()` too, since this typically runs headless (triggered by a keybind/tray, no attached terminal). `popup::show_result` takes the provider name `translate_with_fallback` returned (e.g. `"deepl"`, whichever one actually succeeded, not necessarily `active_provider`) and shows it as `via {provider}` under the heading — same idea as the "Up to date (via lmstudio)" status line `live_translate.rs`/`live_region.rs` already had; `show_history` passes `entry.provider` (already stored in history) for the same display when reopening a past entry.

**Capture backend selection** (`src/capture/mod.rs::acquire`) branches on `cfg.capture.backend`:
- `BuiltIn` (default): `grab_active_monitor()` — platform-specific, see "Cross-platform capture" below — then `select_crop()` shows it in our own zoom/pan/select window (`capture/selector.rs`; there's no portable "overlay the live desktop" API on Wayland, so this grabs a full still image first rather than a live overlay, and the same code is reused as-is on Windows even though a live overlay *would* be possible there — no reason to special-case it yet).
- `External` (`capture/external.rs`): runs a configurable shell command (default: KDE's `spectacle -r -b -c`) that does its own **live** region selection on the real desktop and leaves a PNG on the clipboard, then reads that back via `arboard` — no crop step needed, its output is already the selected region. Diffs the clipboard image against a pre-command snapshot to avoid mistaking a stale clipboard image for a fresh one (same guard the bash prototype this was based on used a hash-polling loop for). **`arboard` needs the `wayland-data-control` Cargo feature** (see comment in `Cargo.toml`) — without it, arboard silently uses its X11 backend even when `WAYLAND_DISPLAY` is set, and can't see what a Wayland-native tool like `wl-copy`/`spectacle` placed on the clipboard (confirmed by testing: `get_image()` returned `ContentNotAvailable` every time until this feature was added). Don't remove that feature flag. This backend is plain shell-command + clipboard-image reading, no Linux-specific code at all — should already work on Windows/macOS with an appropriate `external_command` (e.g. a PowerShell snippet, or ShareX), completely independent of the `BuiltIn` backend work below.

**Cross-platform capture** (`src/capture/mod.rs`): `grab_active_monitor`, `primary_monitor` (used by `clamp_to_screen`), and the Linux-only submodules (`portal`, `monitor`, `pointer`, `screencast`) are all `#[cfg(target_os = "...")]`-dispatched from `mod.rs`, which also defines the shared `MonitorRect` struct every backend returns. Not a trait/dyn-dispatch abstraction — deliberately just `#[cfg]` blocks per platform, since there's exactly one implementation per OS and no runtime switching needed.
- **Linux**: `capture/portal.rs` (xdg-desktop-portal `Screenshot`, the only portable way to get pixels on Wayland — there is no X11 fallback) crops down to just the monitor under the cursor; `capture/pointer.rs` gets cursor position and `capture/monitor.rs` gets monitor layout, both via a direct XWayland query (works even though this is a Wayland session — XWayland mirrors the real cursor position and output layout, and there's no portable Wayland API for either). `capture/monitor.rs` queries monitor geometry via a direct XRandR `GetMonitors` request over `x11rb` (with the `randr` Cargo feature enabled), **not via `xcap`** — a dependency this project used and dropped. `xcap` 0.9+ has every geometry accessor (`Monitor::x()/y()/width()/height()`, and `Monitor::from_point()`, which calls those internally) unconditionally call an internal Wayland scale-factor lookup that hangs indefinitely on at least this project's KDE/KWin test setup (confirmed by tracing the hang to `get_scale_factor()` → `libwayshot_xcap::WayshotConnection::new()`, which spams `Ignoring a wl_output with version < 4` and never returns). Re-confirmed still true as of `xcap` 0.9.8 by reading its current `Cargo.toml`: its Linux target dependencies still include a `libwayshot-xcap` fork — the same wayshot-based code the hang was traced to, not something fixed in a newer release. **Don't reintroduce `xcap` on Linux.**
- **Windows** (`capture/windows_backend.rs`): uses `xcap` — deliberately scoped to `[target.'cfg(target_os = "windows")'.dependencies]` only (see the Cargo.toml comment), so it shares no code path with the Linux backend and the above hang can't recur here even if `xcap`'s Linux backend regresses further. The `wgc` Cargo feature (opt-in Windows.Graphics.Capture) is deliberately **not** enabled — `xcap`'s default Windows path (feature disabled) uses plain GDI `BitBlt` instead (confirmed by reading `xcap`'s `src/windows/capture.rs`: `capture_monitor` is `#[cfg(feature = "wgc")]`-gated between a `wgc::capture_monitor` and a `gdi::capture_monitor` implementation), which is also the same simple, proven approach a mature real-world tool (ShareX) uses for its own screenshots — the `wgc` path has real open upstream issues (capture timeouts, COM object lifecycle bugs) that plain GDI sidesteps entirely. `xcap` has no cursor-position API (it's a screen-capture library, not an input-query one), so `windows_backend.rs` calls Win32 `GetCursorPos` directly via the `windows` crate (same version `xcap` itself already depends on). **Not yet verified on real Windows hardware** — CI (`.github/workflows/autobuild.yml`) only confirms it *compiles*; see `TODO.md` before assuming it actually produces correct screenshots.

**Windows local build & run environment — five real gotchas confirmed on an actual Windows VM while getting this working, all now in README's Windows requirements**, in the order they bite:
1. Use `rustup` + the `-msvc` Rust ABI, not `-gnu`. A Chocolatey `choco install rust` install defaults to `-gnu`, which fails with `error calling dlltool 'dlltool.exe': program not found` compiling `windows-sys` (it needs `raw-dylib` linking, which the GNU toolchain needs a MinGW-provided `dlltool` to resolve; MSVC doesn't hit this). **Having `choco install rustup.install` alongside an old `choco install rust` isn't enough** — Chocolatey's `bin` directory sits on the system-wide `PATH` ahead of rustup's user-level one, so its binaries silently win regardless of `rustup default`/`rustup show` (confirmed: `rustup show` reported `msvc` while `rustc --print cfg` still showed `target_env="gnu"`, traced to `Get-Command cargo -All` listing the Chocolatey path first). `choco uninstall rust` + a fresh terminal is the real fix; don't trust `rustup show` alone to confirm which toolchain is actually active on Windows, check `rustc --print cfg` too.
2. MSVC needs `link.exe` from Visual Studio's "Build Tools" (Desktop development with C++ workload) — without it: `error: linker `link.exe` not found`.
3. `leptess`/`tesseract-sys`/`leptonica-sys` need `VCPKG_ROOT` actually set (not just vcpkg installed and on PATH) — without it: `VcpkgNotFound("No vcpkg installation found...")`. This bit CI too (`autobuild.yml`'s Windows job originally only ran `vcpkg install` without ever setting `VCPKG_ROOT`) — fixed there by bridging the runner's pre-set `VCPKG_INSTALLATION_ROOT` into `VCPKG_ROOT` via `$GITHUB_ENV`, since those are two different variables and the `vcpkg` Rust crate only reads the latter.
4. Once vcpkg resolves correctly, `leptonica-sys`/`tesseract-sys`'s `bindgen` step needs `libclang` — without LLVM installed: `Unable to find libclang: "couldn't find any valid shared libraries matching: ['clang.dll', 'libclang.dll']..."`. Fixed with `choco install llvm` (or winget/the official installer) + a fresh terminal, `LIBCLANG_PATH` set explicitly as a fallback. **CI doesn't need this** — confirmed via GitHub's own `runner-images` software manifest that `windows-latest` ships LLVM pre-installed, so this is purely a local-machine gap, not something `autobuild.yml` needs to account for.
5. **The build succeeding isn't the end of it — running the resulting exe can still fail.** Confirmed on a real Windows machine: a successful `cargo build --release` produced an exe that immediately hit `The code execution cannot proceed because tesseract55.dll was not found. Reinstalling the program may fix this problem.` on launch. Cause: `VCPKGRS_DYNAMIC=true` (needed for step 3 above to resolve at all) makes `leptonica-sys`/`tesseract-sys` link Tesseract/Leptonica *dynamically*, so the exe depends on `tesseract55.dll` plus its transitive dependencies (Leptonica, libpng, zlib, libjpeg-turbo, libwebp, libtiff, openjp2, etc.) being discoverable at runtime — vcpkg builds these into `%VCPKG_ROOT%\installed\x64-windows\bin\` but does **not** put that directory on PATH or next to the built exe for you. Fix for a local dev build: copy every DLL from that directory next to `target\release\ocr-translate.exe` (or add the directory to PATH). `autobuild.yml`'s `release-windows` packaging step does this automatically for the shipped release archive (see below) — don't assume a locally-built exe you copy elsewhere will just work without carrying those DLLs along.

**Two more real bugs found once the exe actually ran** (same Windows VM, after fixing #5 above):
- **Tray icon showed up but didn't respond to right-click at all.** Root cause: `tray::run_native_tray` (the non-Linux path in `src/tray.rs`) just slept in a loop — `tray-icon`/`muda` create a hidden Win32 window on Windows and rely on that thread pumping window messages (`PeekMessageW`/`DispatchMessageW`) for clicks/menu selection to be delivered at all; with no message pump, the icon existed but Windows never delivered it anything. Fixed by replacing the sleep loop with a real `PeekMessageW`-based pump (`PM_REMOVE`, so it doesn't block indefinitely — the same loop iteration still needs to periodically poll `history.jsonl` for the History submenu refresh) — verified compiling+linking via an isolated cross-compiled scratch crate (same technique used for Phase 1's `windows_backend.rs`), since there's no Windows machine in this dev environment to test on directly.
- **`egui_glow: OpenGL: egui_glow requires opengl 2.0+`** on every `eframe` window (`capture`'s crop selector, `watch-clipboard`'s live popup). This is a VM display-driver limitation, not an app bug: confirmed on a KVM/libvirt guest using the default `<video model type="qxl">` — QXL is a paravirtualized 2D-only display device with no 3D/OpenGL support at all, so `eframe`'s `glow` backend (real OpenGL, no software fallback bundled) can't get a usable context. Real GPU passthrough (VFIO) or a 3D-capable virtio-gpu setup would fix this the "real" way, but Windows-guest support for virtio-gpu 3D acceleration under QEMU is still immature — the practical fix instead is dropping software-rendering `opengl32.dll` **and** `libgallium_wgl.dll` (e.g. from the `pal1000/mesa-dist-win` project's prebuilt Mesa/llvmpipe Windows binaries — confirmed both files are needed, not just `opengl32.dll` alone) next to the exe, which gives a fully spec-compliant OpenGL context in software regardless of the guest's display device. If this keeps biting real (non-VM) Windows hardware too — e.g. a machine with a broken/missing GPU driver — switching `eframe`'s renderer from `glow` to `wgpu` (which can fall back to Windows' always-available software Direct3D rasterizer, WARP) would be a more robust long-term fix; not done yet since it's a real dependency/architecture change that needs justification from more than one VM's worth of evidence.
- **`failed to initialize Tesseract (is 'tessdata' for the configured language installed?): TessInitError{-1}`** once `capture` actually ran. Not a bug, same underlying requirement Linux already has (see the Linux Requirements section in README: "at least one language's tessdata installed") — vcpkg's `tesseract` port only provides the OCR engine library, never the trained `.traineddata` language files, and nothing else in the Windows setup steps above installs them either. Fix: download the needed `.traineddata` file(s) (matching `cfg.ocr.languages`) from the official `tesseract-ocr/tessdata_fast` (or `tessdata`/`tessdata_best`) GitHub repo, then either set `ocr.tessdata_dir` in config to that folder or set the `TESSDATA_PREFIX` env var. (The error text also showed up *inside* a Live Clipboard Translate window in one test — that's not a second bug or an OCR/translate interaction: `watch-clipboard` never touches Tesseract at all, it was just translating the literal error string because that's what happened to be on the clipboard at the time, e.g. from copying the `capture` error popup's text.)
- **macOS**: not started. `grab_active_monitor`/`primary_monitor` fall through to a stub that returns a clear "not implemented on this OS yet" error / `None` respectively.
- **Live Region Translate is Linux-only for now**: `src/live_region.rs` (real implementation) is only compiled with `#[cfg(target_os = "linux")]` in `main.rs`; other platforms get an inline stub `run()` that returns a clear error, so `watch-region` exists as a command everywhere (the tray menu item, the CLI subcommand) but only works on Linux until this is picked up — see `TODO.md`'s Phase 5 for the planned approach (try `xcap`'s own screen-recording API first, fall back to shelling out to `ffmpeg` the way ShareX itself does for its screen recorder).
- **CJK font fallback on Windows**: no fontconfig to query, so `src/fonts.rs::find_cjk_font_path` just checks a short hardcoded list of fonts Windows itself commonly ships (Yu Gothic, MS Gothic, Meiryo, Microsoft YaHei, SimSun, Malgun Gothic) under `%SystemRoot%\Fonts`, same "silent no-op if none found" philosophy as Linux. Not yet verified on real Windows hardware either.
- **Exe icon (Windows only)**: `build.rs` + the `winresource` build-dependency embed `assets/icon.ico` (generated from `src/logo.jpeg` via ImageMagick, multi-resolution: 16/32/48/64/128/256px) as the built exe's icon resource, so it shows up in Explorer/the taskbar for the file itself — separate from the runtime window/tray icons `src/icon.rs` sets from the same source logo. **Deliberately not a target-gated Cargo dependency** (unlike `xcap`/`windows` above) — build scripts always compile for the *host* running the build, not `--target`, so gating `winresource` behind `[target.'cfg(target_os = "windows")'.build-dependencies]` would only make it available when the host itself is Windows, silently breaking a genuine Linux-host cross-compile for Windows (confirmed by testing: build.rs failed with "unresolved crate `winresource`" under exactly that gating). `winresource` is a real no-op on non-Windows hosts (only depends on the portable `version_check`, confirmed compiling on Linux) and its own docs recommend deciding what to do at runtime via `CARGO_CFG_TARGET_OS` instead of `#[cfg(target_os = "windows")]` for exactly this reason — `build.rs` does the same. Verified end-to-end (icon resource genuinely present, a `.rsrc` PE section) via the same isolated-cross-compile technique used elsewhere in this project (a scratch crate cross-compiled for `x86_64-pc-windows-gnu`, checked with `objdump -h`) — not yet confirmed the icon actually *displays* correctly in a real Windows Explorer window.
- **No console window on double-click (Windows only)**: `src/main.rs` sets `#![cfg_attr(target_os = "windows", windows_subsystem = "windows")]`, so double-clicking the exe (or a hotkey/tray launching it with no parent console) doesn't pop up a console window — matches how a tray-resident GUI app is expected to behave (same as ShareX). This does **not** break `test-provider`/`init-config`/etc.'s stdout when run from an existing terminal: the `windows_subsystem` attribute only controls whether Windows *auto-allocates a new console* at process startup, not whether an already-inherited stdout handle can still be written to — a GUI-subsystem exe launched from an existing `cmd.exe`/PowerShell session still writes to that same console normally. (One real caveat: legacy `cmd.exe` specifically doesn't block waiting for a GUI-subsystem child the way it does for a console one, unlike PowerShell — not a concern for this project's actual invocation paths, since hotkeys/the tray launch the exe directly, not through `cmd.exe`.) Verified the subsystem is actually set correctly (PE header shows "(GUI)" via `file`, cross-compiled for `x86_64-pc-windows-gnu`) — the stdout-still-works-from-a-terminal claim is standard, well-established Windows behavior, not something re-derived from scratch here, but like everything else Windows-specific in this project, not yet confirmed on real hardware.

**Config** (`src/config.rs`): lives in `~/.config/ocr-translation/` (Linux; `dirs::config_dir()` gives the OS-correct equivalent elsewhere), auto-created with a starter `config.yaml` plus `config.example.{yaml,conf}` reference copies on first run if missing. Both `.yaml` (via `serde_yaml`, full nested structure with `#[serde(default)]` at every level) and `.conf` (hand-written INI parsing in `load_ini`, since INI has no native nested-struct mapping) must be kept in sync manually — if you add a config field, update the relevant struct *and* `load_ini`'s match arms *and* both example files in `config/`. `ProviderConfig.kind` (`openai_compatible` | `google_translate` | `bing_translate`) drives which `translate/*.rs` implementation gets built in `translate::build_for`; `ProviderConfig.mode` (`public` | `private`) further branches Google/Bing between their free unofficial endpoint and their official authenticated API (ignored for `openai_compatible`).

**Window-config sections are split by what they show, not by which command triggers them** — a deliberate reorganization, don't collapse them back together:
- `popup` (`CaptureWindowConfig`: width/height/always_on_top, no font_size/auto_close_secs) sizes the **crop-selector window** — "drag a rectangle to select" — shared by both `ocr-translate capture` (BuiltIn backend, `capture::acquire` → `capture::select_crop`) and `watch-region`'s initial region pick (`live_region::run` → `capture::select_region_rect`). Its `width`/`height` aren't a literal window size, they're the box `capture::selector::fit_scale` scales the screenshot to fit within (aspect ratio preserved) before the user can zoom further — see the doc comment on `fit_scale`.
- `translate` (`PopupConfig`: width/height/font_size/always_on_top/auto_close_secs) is shared by **every window that shows a translation result**: the one-shot `capture` popup (`popup::show_result`), Live Clipboard Translate, and Live Region Translate. `auto_close_secs` only does anything in `popup::show_result` — `live_translate.rs`/`live_region.rs` read `cfg.translate.width/height/font_size` for appearance but never look at `auto_close_secs`, since auto-closing a window that's supposed to keep updating in place would end the "live" session early. If a live window ever needs auto-close as a deliberate feature, that has to be new, explicit logic — not just wiring up the shared field.
- `history_popup` (`PopupConfig`, unchanged) is the popup shown when reopening a history entry (`main.rs::show_history`) — kept separate from `translate` so it can be sized differently (e.g. larger, for comfortably re-reading old entries) than the live capture-result popup.
- `live_translate`/`region_translate` now hold *only* mechanism-specific fields (`show_source_by_default`, `poll_interval_ms`, and for region also `capture_delay_secs`) — their old width/height/font_size/always_on_top fields moved into `translate` above. `live_region.rs` also reads `cfg.popup` (not `cfg.region_translate`) for the region-selection window, matching the "popup = crop-selector, shared across capture and live-region" rule.

**Any configured window size (`popup`/`translate`/`history_popup` width+height) is passed through `capture::clamp_to_screen` before being handed to `egui::ViewportBuilder::with_inner_size`** (`capture/selector.rs`, `popup.rs`, `live_translate.rs`, `live_region.rs` all do this; do the same for any new window whose size comes from config). Confirmed by testing on a KDE/KWin Wayland session: requesting an inner size where *both* dimensions are within ~10px of the primary monitor's actual resolution (3440x1440 in testing) makes the window render as a tiny fallback-sized box in the top-left corner instead of the requested size — `with_maximized(true)` hits the identical broken result, so this isn't a "use maximize instead" fix. `clamp_to_screen` (`src/capture/monitor.rs`) just subtracts a small safety margin from whichever dimension(s) would otherwise land in that zone, using the same XRandR monitor query as `capture::monitor::primary_monitor`. If a user reports a popup/live-window "not opening at the size I configured," check whether their configured size is at or near their monitor's exact resolution before assuming it's a new bug — it's probably this one, and the fix is the clamp, not a bigger window request.

**Translation providers** (`src/translate/`) all implement the small `Translator` trait. `openai_compat.rs` is the general-purpose one — it's how LM Studio, Ollama, OpenAI, and DeepSeek are all supported through a single implementation (any `/chat/completions`-shaped API), configured entirely via `ProviderConfig` (base_url/model/api_key) rather than needing provider-specific code. `google.rs`/`bing.rs`/`deepl.rs` are real translation APIs (not LLMs, so they never send `prompt.system`/`prompt.template`), each with `mode: public`/`mode: private`. DeepSeek is `openai_compatible`, not a dedicated translation API, and is not to be confused with **DeepL** (`deepl_translate`) — a real, separate translation service; it has no free/public mode to add either; don't try to invent one.

**All three `public` modes are modeled directly on [XUnity.AutoTranslator](https://github.com/bbepis/XUnity.AutoTranslator)'s free Google/Bing/DeepL endpoint implementations** (`src/Translators/{GoogleTranslate,BingTranslate,DeepLTranslate.ExtProtocol}` in that repo, MIT-licensed same as this project) — read directly from their source, not just their docs (which don't cover request formats). Each works the same general way: load the provider's real translator web page once to get a session (a scraped token and/or cookies), reuse that session across many translations, and refresh it periodically rather than on every call — see `session::SessionCounter`, shared by all three (`GoogleSession`/`BingSession`/`DeepLSession`, each a small `HashMap<provider_name, Session>` behind a module-level `OnceLock<Mutex<..>>`, so a session survives across calls within one process — matters for `watch-clipboard`/`watch-region`, which call `translate_with_fallback` repeatedly in the same process; `capture` is a fresh process every time regardless).
- **Google** (`google.rs`): a "tk" anti-abuse token computed per-request from a session-wide `TKK` seed (`m`/`s`, two integers) scraped out of `translate.google.com`'s HTML (`tkk:'m.s'`/`TKK='m.s'`) — falls back to hardcoded values (matching XUnity's own fallback) if scraping fails, which in practice still works fine (confirmed: this project's own scrape attempt didn't find the marker at all against the live page today, and the fallback constants were used successfully anyway). The `tk`/`Vi` bit-manipulation functions in `google.rs` are a direct port of XUnity's `Tk`/`Vi` (itself credited there to "Translation Aggregator r190, Sinflower") — this is reverse-engineered from Google's obfuscated client JS, not a documented algorithm, so don't "simplify" it without re-verifying against the live endpoint.
- **Bing** (`bing.rs`): needs `IG`/`IID` scraped from `bing.com/translator`'s HTML *plus one thing XUnity's BingTranslateEndpoint doesn't scrape*: a `token`/`key` pair from `params_AbusePreventionHelper = [key, "token", ttlMs]`, appended to the request as `&token=...&key=...`. Confirmed by testing that XUnity's exact request shape (IG/IID + cookies, no token/key) gets rejected by the live endpoint today with `{"statusCode":205}` (the page's own JS treats that as "stale session, reload") — Bing evidently added this requirement after XUnity's implementation was last touched. Don't revert to the IG/IID-only shape; it's confirmed not to work.
- **DeepL** (`deepl.rs`): a JSON-RPC endpoint (`LMT_handle_jobs` on `www2.deepl.com/jsonrpc`), needing a `getClientState` priming call first and a `timestamp` value massaged per a quirk XUnity's `ExtDeepLTranslate` implements (round up to the next multiple of `1 + count_of('i' in the text)`) — ported as `massaged_timestamp`. **Less proven than Google/Bing**: the one live attempt made while building this got HTTP 429 immediately, and further automated testing against DeepL's endpoint got blocked by this environment's own tool-safety layer, so this implementation has not been confirmed working end-to-end the way Google/Bing have — treat `mode: private` (a real DeepL API key) as the reliable option for DeepL specifically until someone confirms `public` mode works live. The `"auto"` source-language handling here is this project's own best-effort guess (XUnity's DeepL support has no auto-detect equivalent to check against), not a confirmed-working behavior.

`translate::translate_with_fallback` (`src/translate/mod.rs`) tries `active_provider` then each of `fallback_providers` in order, returning the first success — used by the real capture pipeline. `translate::build`/`build_named` (single provider, no fallback) are used by `test-provider`, which is deliberately not fallback-aware since its whole point is to surface one provider's real error.

**CJK font fallback** (`src/fonts.rs`): egui's bundled default fonts only cover Latin script, so Japanese/Chinese/Korean text rendered as tofu boxes until this was added. Rather than embedding a CJK font (a full-coverage one like Noto Sans CJK is ~20MB), `install_cjk_fallback` shells out to `fc-list :lang=ja file` (not `fc-match`, which happily returns an unrelated font even with zero CJK support on the system) to find whatever CJK-capable font is already installed, reads it from disk, and appends it as a fallback on egui's `Proportional`/`Monospace` font families. Confirmed this correctly loads a `.ttc` (TrueType Collection, e.g. `NotoSansCJK-Regular.ttc`) via `egui::FontData`'s face `index` field — not just plain `.ttf`/`.otf`. Every `eframe::run_native` closure in this crate (`popup.rs` ×2, `capture/selector.rs`, `live_translate.rs`, `live_region.rs`) calls this on `cc.egui_ctx` before returning the app; do the same for any new window. If no CJK font is found, this is a silent no-op (logged at debug level) rather than an error — better to render boxes than to fail the whole popup.

**History** (`src/history.rs`): JSON Lines at `history.jsonl` next to the config file, one `HistoryEntry` per line, newest appended last, trimmed to `history.max_entries` on every append (the whole small file is rewritten each time — simplicity over micro-optimizing an infrequent, small-file operation). `load_recent(n)` returns the last `n` entries reversed (most-recent-first) for both the tray submenu and `show-history <INDEX>` (0 = most recent).

**Tray History submenu** (`src/tray.rs`): rebuilt periodically (every 2s) rather than once at startup, since captures run in a separate process (see above) — this process only learns about new entries by re-reading `history.jsonl` from disk. On Linux this refresh runs via `glib::source::timeout_add_seconds_local` on the GTK main-loop thread (not a plain `std::thread` + sleep) — GTK/muda tray objects must only be touched from the thread running the GTK main loop, so the refresh closure has to be scheduled onto that loop rather than mutating the `TrayIcon` from elsewhere. A cheap fingerprint (entry count + latest timestamp) avoids rebuilding the menu when nothing changed.

**Live Clipboard Translate** (`src/live_translate.rs`, `watch-clipboard`): a long-lived (not one-shot) eframe window with a background thread polling `arboard::Clipboard::get_text()` (same crate/feature as the image-clipboard `external` capture backend, so the `wayland-data-control` note above applies here too) at `live_translate.poll_interval_ms`. On each poll it compares the current text against the last value it translated (plain string equality; empty/whitespace-only text is skipped) and only re-translates on an actual change — this is intentionally simpler than `capture::external`'s snapshot-diffing, since there's no "stale clipboard from before we started" concern here: on startup it should immediately translate whatever's *currently* on the clipboard. Shared state (`Arc<Mutex<LiveState>>`) is written by the watcher thread and read each frame by the egui `update()`, which reuses `translate::translate_with_fallback` — same fallback chain as capture — but deliberately never calls `history::append`. Don't add a history write here; that's the one thing this command is explicitly not supposed to do.

**PipeWire ScreenCast capture** (`src/capture/screencast.rs`): unlike the one-shot `Screenshot` portal used everywhere else, `watch-region` needs a *continuous* video feed of a fixed region, so it goes through the separate `org.freedesktop.portal.ScreenCast` portal instead — `CreateSession` → `SelectSources` (`CursorMode::Hidden`, `SourceType::Monitor`, `PersistMode::DoNot`) → `Start` (this is what shows the compositor's "share screen with..." picker) → `OpenPipeWireRemote`, which hands back a PipeWire connection fd. `ScreenCastSession::start()` runs that async negotiation on a dedicated thread (its own single-threaded Tokio runtime), then blocks the caller until negotiation succeeds (a `sync_channel` handshake) while the same thread pivots into a synchronous PipeWire main loop (`pw::main_loop::MainLoopRc` + `pw::stream::StreamRc`) that keeps running for the session's lifetime — dropping the `ScreenCastSession` (and thus the portal session/PipeWire core) ends the stream. Frames arrive on the stream's `process` callback (raw `BGRx`/`RGBx`/`BGRA`/`RGBA`, whichever the compositor picked during format negotiation in `param_changed`) and are stashed as the single latest frame in an `Arc<Mutex<Option<RawFrame>>>` mailbox — there's no queue, since a poll-driven OCR loop only ever wants the newest frame, and frames can arrive at 60fps while OCR only samples every second or so. `RawFrame::to_rgba` (stride-aware, byte-order-aware) is deferred until a frame is actually requested via `latest_frame()`, not done in the callback, to avoid wasted conversions on frames nobody asks for.
- **`pipewire` is version-pinned in spirit, not in `Cargo.toml`, but pay attention if bumping it**: `0.8.x` fails to build against this project's system PipeWire (1.6.8) headers — `libspa-sys 0.8.0`'s bindgen output has an opaque `spa_pod_builder` struct incompatible with the real headers. `0.10.1` (and whatever's current — check `cargo info pipewire`) builds cleanly. Verify a real build (not just `cargo check`) after bumping.
- The raw SPA format constants used to build the offered-format Pods (`SPA_FORMAT_mediaType`, `SPA_MEDIA_TYPE_video`, etc.) live in `libspa-sys`, reachable as `pipewire::spa::sys` (`libspa`'s `lib.rs` does `pub use spa_sys as sys;`, and `pipewire`'s `lib.rs` does `pub use spa;`) — not `pipewire::sys`, which is the separate `pipewire-sys` FFI crate for libpipewire itself. Mixing these up is an easy, quiet-looking `E0425` mistake since both crates expose similarly-named `sys` modules.
- Verified by dumping one captured frame to a PNG and visually inspecting it (`image::RgbaImage::save`) before building anything else on top — confirmed correct resolution, colors, and content (a live, real desktop capture, not a stale/black/garbled frame) on this KDE Plasma Wayland + PipeWire 1.6.8 setup.

**Live Region Translate** (`src/live_region.rs`, `watch-region`): opens a `ScreenCastSession`, waits `region_translate.capture_delay_secs` (default 1s) for the compositor's own "share screen with..." picker dialog to actually finish closing — confirmed by testing that without this delay, the very first frames from the stream can still show that dialog, getting it baked into the region-selection screenshot — then waits for the first frame and reuses `capture::select_region_rect` (the same zoom/pan/select UI as `capture::select_crop`, factored to return the chosen `(x, y, w, h)` rectangle instead of an already-cropped image) so the user picks the region once against a live frame. From there a background thread polls `session.latest_frame()` every `region_translate.poll_interval_ms`, crops it to that fixed rectangle, runs it through the same `ocr::recognize` used by `capture`, and only calls `translate::translate_with_fallback` when the OCR'd text actually *changed* from the last poll (text-based dedup, not a pixel/frame diff — deliberately, since OCR noise on an unchanged region should not cause a retranslation, and this is cheaper than diffing raw frames). Like `watch-clipboard`, this never calls `history::append` — don't add one.

## Manual verification

There's no automated test suite, so behavior changes need to be checked by hand:
- `cargo build && ./target/debug/ocr-translate capture` exercises the full pipeline directly (fastest loop for capture/OCR/crop-selector changes).
- **Windows-specific code (`capture/windows_backend.rs`, the `fonts.rs` Windows path) can't be verified in this environment at all** — there's no Windows machine here, and cross-compiling from Linux to Windows locally hit a missing `mingw-w64-gcc` toolchain (needed even for unrelated dependencies like `ring`'s TLS backend) when tried. `.github/workflows/autobuild.yml`'s `release-windows` job (tag-push-only — it was taking 30+ minutes per run, too expensive for every push/PR, so this whole workflow is release-only now, no push/PR build-check jobs) is the actual verification signal for "does this compile on Windows" — and even that only proves it compiles and packages, not that it produces correct screenshots; that needs either real Windows hardware or someone running the binary. Don't claim Windows support works without one of those two checks having actually happened.
- `ocr-translate test-provider --provider NAME "some text"` exercises just the translate leg without any screen interaction — use this for prompt/provider changes.
- For the `external` capture backend, a real interactive test needs a human at the keyboard; to test the clipboard-diffing mechanics deterministically instead, set `external_command` to something non-interactive (e.g. `wl-copy < some.png`) and seed a *different* baseline image on the clipboard first — otherwise capturing the same bytes twice reads as "cancelled" (see the doc comment on `capture::external::capture`).
- `watch-region`'s region-selection step needs a real mouse drag, which can't be scripted here: synthetic input (e.g. `xdotool mousemove`/`click`) does not reliably reach a native-Wayland eframe window on at least this KDE/KWin setup (confirmed: `xdotool getmouselocation` after a `mousemove` showed the pointer hadn't actually moved) — don't rely on it, and don't force it by clicking blindly on the real desktop. What *can* be verified without a human: that `ScreenCastSession::start()` negotiates the portal and delivers correct frames (dump one to a PNG, as above), and that the selector window opens showing that live frame — cancelling it (closing the window without dragging) should log "region selection cancelled" and exit cleanly with no OCR/translate/history side effects.
- Tray behavior needs an actual running desktop; a `com.canonical.dbusmenu` `Event` D-Bus call against the tray's menu object path (visible via `busctl --user` / the `org.kde.StatusNotifierWatcher`'s `RegisteredStatusNotifierItems`) can simulate a real menu click without needing to drive a mouse, which is how tray wiring (including the History submenu and Clear History) has been verified in this environment. Use `GetLayout` first to find the numeric ids of the items you want to click.
- Kill stray `ocr-translate` processes between test runs (`pkill -x ocr-translate`, not `pkill -f ocr-translate` — `-f` matches the full command line, which will match your *own* shell command if it happens to mention "ocr-translate" anywhere, e.g. in a path or an echoed message, killing the command that's running `pkill` itself; confirmed happening in this project's own testing) — a killed-without-cleanup tray process can leave a stale, non-functional icon visible in the system tray that's easy to mistake for a live one.
- To verify the single-instance lock (`daemon::acquire_single_instance_lock`): start `ocr-translate run` in the background, then start a second one — the second should log an error, show an error popup, and exit, while the first stays completely untouched (`ps -p <first-pid>` before/after). Don't just trust the log line; also confirm the *first* instance's PID is still alive afterward, since the whole point of this mechanism is that it never touches an existing instance.
- The free Google/Bing/DeepL `public` translate modes (`src/translate/{google,bing,deepl}.rs`) genuinely need a live network round-trip against each real service to mean anything — `test-provider --provider google|bing|deepl "some text"` with `general.target_lang` set to something other than the input's language (otherwise "translated" output that's identical to the input looks like a false pass, not a real one) is the fastest check, and translating into a language you can read yourself is the only way to actually confirm the output is a real, sensible translation and not e.g. an echoed/garbled response that happens to parse. Don't test all three back-to-back against the same target in a tight loop — that's exactly the kind of traffic pattern their abuse-prevention exists to catch, and DeepL's in particular has been observed to 429 quickly.
